## 1. 核心技术栈与规范
* **状态管理**：统一使用 getx。不要混用其他状态管理库。
* **网络与长连接**：
    * HTTP/RESTful 请求统一使用 `dio` 库，必须包含拦截器、错误处理和统一的 BaseResponse 解析。
    * 长连接（WebSocket/Socket.io）需封装为单例模式，具备自动重连、心跳检测（Ping/Pong）机制。
* **本地存储**：持久化数据（如用户信息、Token）使用 `shared_preferences`；本地消息缓存与历史记录使用 SQLite。
* **任何未明确的技术方案、逻辑调整以及技术实施过程中任何不明确时，必须请求询问获取最终执行方案,不得私自执行。**

## 2. 代码风格与架构要求
* **架构模式**：采用 Clean Architecture（清洁架构）或分层架构（Data -> Domain -> Presentation）。
* **UI 与业务分离**：Widget 层只负责渲染和接收用户事件，不允许包含任何业务逻辑、网络请求或直接的状态修改。
* **简洁与高密度**：界面设计追求极简主义、高信息密度。组件设计要紧凑，避免臃肿的 padding 和过大的空白。
* **健壮性**：所有 Dart 代码必须开启空安全（Null Safety）。网络解析、JSON 序列化必须有 try-catch 保护，防止因脏数据导致 App 崩溃。
* 交互反馈:
  * **绝对禁止无反馈操作**：所有用户点击、提交、滑动等交互行为，必须有即时的视觉或听觉反馈（如Loading状态、按钮置灰、Toast提示、成功/失败弹窗等）
  * **使用轻量动画:** 反馈动画必须保证流畅，不得引起掉帧或卡顿（优先使用 `transform` 和 `opacity` 等不触发重排的属性）
  * **异步操作必加状态**：涉及网络请求或耗时操作时，必须提供加载中的占位符或骨架屏，并在请求结束后给出明确的结果反馈 (**注：对于列表类请求，若已有历史数据，可直接展示数据并在局部展示Loading；若为首次加载，必须展示骨架屏或占位符**)
  * **错误处理可视化**：当用户输入不合法或操作失败时，必须提供清晰的错误提示文案，严禁默默失败或仅抛出控制台报错。
  * 预期结果必须具体到反馈的形式（例如：‘按钮显示旋转Loading图标，3秒后弹出绿色成功提示’，而不是笼统的‘提示成功’）。
* **全局组件必须完整详细中文注释**

## 3. IM 业务特异性规则（极其重要）
* **消息列表优化**：聊天会话和消息列表必须使用高性能的 `ListView.builder`，实现懒加载（分页），并做好 Item 复用，防止由于大量消息导致卡顿。
* **时间与状态**：消息时间戳、发送状态（发送中、已送达、已读、失败）必须作为独立状态驱动 UI 更新。
* **国际化与文本**：暂不使用复杂的 i18n 框架，提示词和 UI 文本直接使用明确的字符串（或提取为常量配置），确保开发效率。

# Flutter Coding Rules

## Toast Rules

禁止直接调用:

AppToast.info()
AppToast.warning()
AppToast.success()
AppToast.error()

业务代码不得直接显示 Toast。

必须使用:

AppFeedback.show()

或者通过状态通知 UI 层处理。

以下场景禁止 Toast:
- 网络同步
- 后台重试
- websocket状态变化
- 自动刷新
- 生命周期事件

仅允许用户主动操作结果:
- 删除成功
- 保存成功
- 复制成功
- 支付结果
